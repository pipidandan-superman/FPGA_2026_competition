## 编制说明

本文件依据工作区工程日志、审计报告、仿真与板测证据，以及**四平台在本机的原始交互记录**，对项目开发过程中的大模型协作进行归纳，重点保留提示词、模型回答、失败观察、自我纠错、人工复核与分层验收之间的关系，而不是只罗列最终成功结果。

**V2.0 相对 V1.0 的修订要点**：

1. V1.0 成稿时标注了两处证据缺口（"Zcode 原始会话尚未检索到"、"Codex 部分原始会话文件已不在原记录路径"）。V2.0 已在本机完成四平台原始存储的定位与只读抽取归档，**两处缺口全部补齐**：Codex 历史会话以 zstd 压缩格式存放于 `~/.codex/sessions`（V1 检索时被遗漏），Zcode 会话存于本地 SQLite 数据库。V1.0 作为历史快照保留，正式提交以本版为准。
2. 引号内文字均为原始记录逐字摘录；标注"据工程记录概括"的提示词与回答为二手摘要，不冒充逐字对话。
3. **脱敏与安全边界**：全部抽取脚本对 API 密钥形态字符串（`sk-…`／`pk-…`／`eyJ…`）做正则替换为 `[REDACTED-KEY]`；`~/.codex/auth.json`、Zcode `config.json` 的 apiKey 与证书、Kimi 桌面端 token-store 等敏感库**绝不复制**，只以只读方式打开会话库。
4. **ChatGPT 口径**：本机可核验的 ChatGPT 家族工具为 Codex CLI／桌面端（rollout 会话记录）；网页版 ChatGPT 在本机无会话存储，不纳入本文件，也不以其他平台记录冒充。

## 一、提交要求与总体协作模式

竞赛要求提交能够体现大模型协作过程的交互记录，包括提示词、模型回答与自我纠错轨迹，并将协作经验沉淀为可复用 Skill。技能包应说明适用范围、使用方法、失效条件和已验证效果。

本项目采用"人工定义目标与边界 → 大模型生成方案或代码 → 真实工具执行 → 原始证据检查 → 模型或人工纠错 → 分层验收 → Skill 沉淀"的协作模式。大模型不是最终验收者：仿真、构建、板测和用户实机目检分别承担不同层级的验收职责。

## 二、各平台协作分工概述

### 2.1 Claude Code

承担三类任务：一是对方案和已有工程进行只读审核（早期经 ROSS 委派，10-11 起直接入场）；二是通过 ROSS／Vivado MCP 执行 lint、仿真和状态检查；三是对"完成"结论进行独立复核。后期演化为"主工程席 + 独立审计席"双会话互审结构（案例 C-05）。其价值不仅是生成代码，更在于发现执行链、验收范围和证据链中的问题。

### 2.2 ChatGPT／Codex

工程前期（09-01 → 10-11）的主力席位：工程初始化、GitHub 管理、摄像头寄存器审计、SD 部署应急、Overlay／PYNQ 工作流与项目规则沉淀。典型纠错包括编辑工具误用循环、位流下载成功被误当系统功能成功，以及平台自身的基础设施故障（176 条错误轨迹，案例 X-07）——后者直接推动了 10-11 向 Claude Code 的席位迁移。

### 2.3 Kimi

三线并用：一是工程执行（三任务 OSD 修复、完整 PL 性能优化、PS+PL 混合推理，案例 K-01～K-03）；二是**策略外脑**——在关键决策点用独立会话对工程现状做只读梳理与重规划（案例 K-05），与其他席位的执行结论形成交叉检验；三是报告与表达（技术报告、创新点提炼、配图、评分预估）。

### 2.4 Zcode

轻量快答与资料定位席位（09-08 → 09-21，10 会话 1147 条消息）：工程速览、概念答疑（PYNQ／FSBL／bundle）、配置核查（YOLO 输入尺寸）、进度盘点，以及两次危机排查（以太网色差、GitHub 分支失控）。特点是从不直接改工程，先读 README／HANDOFF 与既有文档再回答，回答可回溯到仓库内具体文件。

## 三、Claude Code 代表交互与纠错轨迹

### C-01：RTL Lint 中空报告被解析器误读出两条记录（2026-10-03，ROSS 委派）

**任务提示词（原始提示词节选）**

> "Use the vivado-rtl-lint skill … Task: lint one RTL file in non-project mode … Use vivadoExecute for ALL Vivado commands … Never create .tcl files … Violation count in the markdown must exactly match Vivado's stated total; if Vivado says 0, report 0."

**模型回答与执行**

模型通过 Vivado MCP 启动 TCL 会话，以非工程方式读取 `yolo_silu_lut.v`，执行 `synth_design -lint`，再调用解析脚本生成 CSV。Vivado 原始报告给出 `Total of 0 linter message(s) generated.`，最终 lint 结果为 0 error、0 warning、0 violation。

**失败观察与自我纠错**

解析脚本在"零违规"空表上生成了两行伪 CSV 数据。模型没有直接把两行写成违规，而是核对 Vivado 原始总数，确认它们来自 `create_waiver` 帮助页脚，是解析器在空表边界上的误切片。随后重新生成真正的零行 CSV，同时保留原始错误输出 `lint_report.csv.raw-parser-output.txt`，使"CSV 行数＝Vivado 总数＝Markdown 数量＝0"。

**最终证据**

- `11_AMD_Ross_AgenticAI/evidence/2026-10-03_rtl-lint/nested_session_transcript.jsonl`
- `11_AMD_Ross_AgenticAI/evidence/2026-10-03_rtl-lint/rtl_lint_report.md`

该案例体现了"自动解析结果不能凌驾于原始报告"，也形成保留失败输出、禁止为凑结果删除证据的规则。

### C-02：B3-S3 方案从"单帧三描述符"纠正为"三帧真实桥接"（2026-09-30）

**任务提示词（据工程记录概括）**

对 B3-S3 设计书、能力盘点、L2 原始板测、驱动和 r9 RTL 进行只读工程审核，判断载体复用和门梯是否合理，不修改冻结工程。

**模型回答**

审核结论为"D1 有条件通过；原 S3a 不通过；门梯需修订后才能开工"。复用 r9 作为唯一位流载体合理，但把 L2 三段写成单帧内三个 descriptor，无法插入真实的 PS gather、buf patch 和 repack 操作，不能证明生产者输出被消费者真实使用。

**纠错轨迹**

原方案以"单帧三 descriptor 连续执行"作为 L2 级联门。审核后改为：

`frame A conv0 → 完成并闭帧 → PS gather／HWC＋buf patch → frame B mp5 → 完成并闭帧 → PS repack＋mirror patch → frame C conv1`

同时保留 walker-only 多描述符协议测试，但其结果只能命名 `WALKER_MULTI_DESC_PASS`，不能升级为 `L2_CHAIN_PASS`。

**最终证据**

- `4_metrics/logs/2026-09-30_b3s3_claude_audit_run01/AUDIT.md`

沉淀规则："协议测试不能替代真实数据链测试""预载数据不能证明生产者—消费者闭合"。

### C-03：M9"全线收官"结论被独立审计降级（2026-10-09）

**任务提示词（据工程记录概括）**

严格审计 M9 的板测、XSim、RTL、Vivado 实现记录和验收范围，核对"M9 全线收官／M9_INTRA_PASS"是否有充分证据。

**模型回答与纠错**

审计确认代表性 Conv 数据通路在板上可运行，但否定"层内流水已在板上闭合"和"完整 M9 收官"：板上只覆盖 5 个代表 Conv 而非完整 63 Conv；XSim 的 overlap 结果不能替代板上 overlap 证据；连续第二帧计数翻倍说明计数器清零与代际语义未闭合；最终 BIT 哈希、板端时钟和完整 post-route 报告没有形成统一制品链；"5.55 fps 整网代表层"被纠正为"5 Conv 代表 walk 首帧约 180 ms"。最终结论限制为条件化的 `BOARD_REPRESENTATIVE_CONV_PASS`。

**最终证据**

- `4_metrics/logs/2026-10-09_yolo_m9_claude_audit_run01/REPORT.md`

该案例说明模型已经写出的"PASS"也必须接受另一轮证据审计，不能由提交说明或单次首帧结果扩大验收范围。

该会话同时完成了项目历史上第一次方向纠偏：同一天会话快照显示，工程从"紫光同创 Logos-2 畸变矫正（RK3568）"整体切换为 AMD 赛道，README 重写并推送。模型在方向突变时先保留旧目录结构证据（`2_log` 清理、文档迁移均留提交记录），不销毁历史。

### X-02：GitHub 交付准则从复杂 PR 流按用户裁定简化（2026-09-08）

**任务提示词（原始）**

> "你知道目前github准则要求吗"
> "更新github交付准则，不要这么复杂，不再设置软硬件负责人和共同区域，两人直接一人一个分支操作，对方批准才能进行main分支提交"

**模型回答**

先核对仓库现状再回答：找到未提交的 `1_docs/GitHub协同上传准则_草案.md`（`DRAFT_FOR_REVIEW`/`v1.0-draft`），逐条复述 8 条核心要求（main 可运行可回退、禁直推 main、PR 单主域、分支命名、无 4_metrics 证据不得写 PASS、冻结产物保哈希、协作前 `pull --ff-only`、PR 拒收条件），并指出当时工作区状态与草案的冲突风险（本地落后远端 4 个提交、大量未跟踪运行产物），明确"现在不适合直接提交或推送，应先分类"。随后按用户裁定改写为简化版。

## 七、跨平台自我纠错机制归纳

| 纠错类型 | 典型失败 | 纠正方式 | 形成的可复用规则 |
|---|---|---|---|
| 方向纠错 | 选题两次转向（紫光同创→§3.2→§3.3） | 保留旧口径原文仅作历史证据（README 切换声明） | 方向切换留痕，不销毁历史 |
| 工具接口纠错 | 反复调用不存在的批量编辑工具（X-05） | 检查真实工具注册表，限制补丁形状与重试次数 | 先确认工具合同；失败后读现状，不重复同形调用 |
| 流程与环境纠错 | Vivado 会话在而 XSim 子进程无法启动（C-04） | 修子进程 PATH，改结构化三段式 XSim | 连接成功、流程成功、功能成功分别验收 |
| 解析与测试自证纠错 | 空表解析出伪记录（C-01）；TB 与 DUT 同源生成期望（K-01） | 回到原始报告；硬编码字模门、独立几何期望与负控 | 自动脚本、测试平台与 DUT 保持证据独立性 |
| 验收范围纠错 | 代表 Conv 写成整网收官（C-03）；单元 PASS 写成整网 PASS（K-02） | 独立审计、降级结论、列未覆盖项 | 结果标签绑定输入范围、配置与制品哈希 |
| 数据语义纠错 | 左右手势标签与观察者视角相反（K-03） | 追数据集 GT 约定并逐类板测 | 数据语义以原始数据集和实机终审为准 |
| 部署运行纠错 | 端口被孤儿服务占用、运行中文件被覆盖（K-03） | 停链、核对端口归属、完整部署、SHA 校验 | 部署是状态迁移，不是文件复制 |
| 性能路线纠错 | 单元收益无法转化为整网收益（K-02） | 负结果停止、稳定版恢复、真实墙钟复核 | 不以理论收益或局部仿真替代整网实测 |
| 协作规则纠错 | 复杂 PR 流拖慢协作（X-02）；分支清理误删队友分支（Z-04） | 用户裁定简化＋事故后规则升级 | 双人分支互批；事故先取证再恢复 |
| 执行纪律纠错 | 执行席偏离已验证流程、反复自造流程（K-05） | 外脑只读梳理＋重立唯一执行 SPEC | 复用已验证流程优先，禁自写替代 |
| 平台迁移纠错 | 通道 403/502/SSE 超时等 176 条故障（X-07） | 故障留痕，席位迁移至 Claude Code | 协作中断也是记录；不与不稳定通道硬耗 |
